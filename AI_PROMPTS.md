# Задача в одном предложении
За 8 часов собрать рабочий Full-Stack dashboard аналитики продаж менеджеров, который поднимается локально одной командой `docker compose up --build`, автоматически применяет миграции, наполняет БД seed-данными и сразу открывает заполненный dashboard в браузере.

# Ограничения
- Авторизация, регистрация, JWT, OAuth, permissions — НЕ реализуем.
- Mobile-версия — НЕ нужна. Целевой viewport: 1440×900.
- Kubernetes, cloud deployment, микросервисы, admin panel — НЕ нужны.
- Clean Architecture, CQRS, Repository, MediatR — только если реально решают проблему. Если простой модуль можно сделать просто — делай просто.
- Никаких ручных SQL, отдельных команд seed или ручной установки зависимостей для запуска.

# Обязательный стек
- Backend: C# .NET 8+, ASP.NET Core, EF Core, REST API, async/await.
- Frontend: React + TypeScript. Библиотеки на твой выбор: TanStack Query, Zustand или Redux Toolkit, Tailwind / MUI / Ant Design / shadcn, Framer Motion, любая библиотека графиков (Recharts, Tremor, Nivo).
- БД: PostgreSQL. EF Core migrations обязательны.
- Инфраструктура: Docker, Docker Compose.
- Дополнительные библиотеки разрешены, если помогают решать задачу, а не усложняют проект.

# Модель данных (минимум)
- Manager: имя, команда/должность, активность, данные для avatar/initials.
- Customer: имя, компания, сегмент.
- Category: категория товаров.
- Product: название, категория, атрибуты.
- Sale: менеджер, клиент, дата, статус.
- SaleItem: товар, количество, цена продажи, себестоимость.

Статусы: Paid, Cancelled, Refunded.

Вычисляемые показатели:
- Revenue = сумма оплаченных продаж.
- Gross Profit = Revenue − Cost.
- Margin = Gross Profit / Revenue.
- Average Check = Revenue / количество продаж.

Правило для Refunded выбери разумное (например, вычитание Revenue и Cost возвратов из соответствующих агрегатов), применяй его последовательно во всей системе и опиши в README.

# Seed-данные
- Менеджеры: 15–25.
- Клиенты: 50–100.
- Категории: несколько.
- Товары: несколько десятков.
- Продажи: 2 000–5 000.
- Период: минимум 6 месяцев, лучше 12.
- Данные неравномерные: сильные и слабые менеджеры, разные средние чеки, разная маржинальность, сезонность, отмены и возвраты, крупные и мелкие сделки, периоды без продаж у отдельных менеджеров.
- Seed воспроизводим: фиксированный Random seed, после пересоздания БД получаются одинаковые данные.
- БД наполняется автоматически после первого запуска без ручных команд.

# Dashboard (desktop, 1440×900)
Обязательные блоки:
- KPI-карточки: выручка, валовая прибыль, маржинальность, количество продаж, средний чек, лучший менеджер. Сравнение с предыдущим сопоставимым периодом.
- Период: сегодня, 7 дней, 30 дней, этот месяц, прошлый месяц, произвольный from → to.
- Рейтинг менеджеров: минимум два режима — по Gross Profit и по Average Check. В строке: позиция, менеджер, количество продаж, выручка, валовая прибыль, средний чек, маржинальность, изменение к предыдущему периоду.
- Динамика: график Revenue / Gross Profit / количества продаж во времени.
- Категории и продукты: продажи и прибыль по категориям, лучшие продукты.
- Последние продажи: дата, менеджер, клиент, товары, статус, сумма, валовая прибыль.

Дополнительно приветствуется: сравнение менеджеров, sparklines, scatter или bar charts, распределение продаж и маржи, доля категорий.

# Backend и API
- Основные вычисления и фильтрация — на сервере. Frontend не должен загружать тысячи продаж и пересчитывать весь dashboard в браузере.
- Понятные REST-контракты, разумное разделение ответственности.
- Эффективная работа с PostgreSQL, отсутствие очевидных N+1.
- async I/O, валидация, понятная обработка ошибок.
- Расширяемая, но не переусложнённая структура.

# PostgreSQL
- EF Core migrations.
- Разумные связи и типы данных.
- Индексы там, где они действительно нужны.
- Корректные aggregate queries.
- Понимание, какой SQL генерирует ORM. Для отдельной аналитической выборки можно raw SQL / Dapper, если это оправдано.

# Frontend и UX
- Современный, визуально аккуратный, информативно насыщенный, легко читаемый интерфейс с понятной иерархией.
- Отзывчивый на desktop.
- Анимации: появление KPI-карточек, animated counters, переходы графиков, hover states, плавное перестроение рейтинга, skeleton loading, transitions таблиц, feedback на действия.
- Обязательные состояния: initial loading, loading при смене периода, ошибка API, пустой период без продаж, отсутствие данных по отдельному блоку. Вечный spinner, белый экран или внезапно пустой блок без объяснения — недопустимы.

# Edge cases (учти и проверь)
- Cancelled и Refunded продажи.
- Менеджер без продаж за период.
- Одинаковые результаты двух менеджеров.
- Продажа ровно на границе диапазона дат.
- Одна очень крупная продажа.
- Большое количество мелких продаж.
- Разные себестоимости и маржа.

# Тесты
- Backend: расчёт KPI, фильтр периода, рейтинг, обработка статусов продаж.
- Frontend: смена периода, переключение рейтинга, loading/error state.
- Не гонись за coverage — покрой то, что реально ломает бизнес-результат.

# Автоматизация AI_PROMPTS.md (сделай в первую очередь)
Настрой автоматическое сохранение моих промптов в `AI_PROMPTS.md` через Cursor Hook `beforeSubmitPrompt`:
1. Создай файл `.cursor/hooks.json` с хуком `beforeSubmitPrompt`, который вызывает bash-скрипт.
2. Создай скрипт (например, `.cursor/hooks/save-prompt.sh`), который:
   - читает JSON со stdin (Cursor передаёт данные промпта);
   - извлекает текст моего сообщения;
   - добавляет timestamp в формате `HH:MM`;
   - дописывает запись в `AI_PROMPTS.md` в формате `## HH:MM – Cursor` + текст;
   - пропускает сообщения короче 15 символов;
   - пропускает строки, содержащие `API_KEY`, `SECRET`, `TOKEN`, `PASSWORD`.
3. Проверь, что скрипт имеет права на выполнение, и объясни, как проверить, что хук срабатывает.
4. Если `jq` не установлен, реализуй парсинг без него или добавь инструкцию по установке.
5. Создай начальный `AI_PROMPTS.md` с заголовком и первой записью — этим самым промптом.
6. Создай шаблон `AI_NOTES.md` с заголовками для рефлексии.
